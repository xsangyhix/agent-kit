# Agent kit

The agent kit is the project-agnostic agent setup: workflow documents, issue-tracker
conventions, guardrails, and the skill library. `agent-kit init` installs it into a
project, and `agent-kit update` moves that project to a newer version. rc-machines is
its first user.

## What it is

The kit gives a project one setup that any coding agent can follow. It installs the
workflow state machine, the local markdown issue tracker, the domain-docs layout, a
pre-commit hook, and a snapshot of Matt Pocock's skill library into `.agents/`. A short
block in `AGENTS.md` points agents at those files. Everything is plain files in the
project's git repository, and the kit records what it installed in `.agents/kit.lock`
so it can refuse to overwrite a project's own edits. opencode is the only supported
harness for now; later harnesses plug into the same installation.

## The kit block

The kit owns the region of `AGENTS.md` between `<!-- agent-kit:begin -->` and
`<!-- agent-kit:end -->`. A marker counts only when it stands on a line of its own: a
line, with trailing whitespace and a trailing `\r` removed, must equal the marker
exactly. Leading whitespace means the line is not a marker, and marker text inside a
line of prose or an indented line is ordinary text: `init` and `update` neither count
it nor touch it. Real marker lines are rewritten in canonical form, so trailing spaces
on them are dropped. Everything outside the marker lines stays the project's.

## Requirements

- **Python 3.14 or newer.** The `agent-kit` tool and the scripts it installs target
  Python 3.14.
- **git** on the developer's machine. `init` and `update` only work in the root of a
  git work tree, and they set `core.hooksPath` there.
- **A POSIX `sh`** for the pre-commit hook. Git for Windows provides one, so a
  Windows checkout needs no extra shell.

The project itself can be written in any language. The kit only adds files under
`.agents/`, the AGENTS block, and a few project-owned starters.

## Install the tool

Replace `<path-to-this-repo>` with the path to your checkout; a published package name
will replace it once there is a release.

With pipx (the `--python 3.14` is required because pipx otherwise picks the system
Python):

```
pipx install --python 3.14 <path-to-this-repo>
```

Or with uv:

```
uv tool install --python 3.14 <path-to-this-repo>
```

Check it:

```
agent-kit --version
```

To upgrade the tool, reinstall it:

```
pipx install --force --python 3.14 <path-to-this-repo>
```

or, with uv:

```
uv tool install --force --python 3.14 <path-to-this-repo>
```

The tool and the kit are separate: upgrading the installed tool does not change any
project. Run `agent-kit update` in each project to move it to the new version.

To work on the kit itself without installing it, run it from the agent-kit repository
root with `pip install -e .` and then `py -3.14 -m agent_kit`, or set `PYTHONPATH=src`.

## Start a project

Run this from the project's git root, or pass the path:

```
agent-kit init [PATH]
```

`init` refuses a folder that is not a git work tree root, an unknown `--harness`, or a
project that already has `.agents/kit.lock`. Use `--harness opencode` to name the
harness explicitly (opencode is the default and the only value today).

What it creates:

| Path | Owner | Written by |
| --- | --- | --- |
| `.agents/kit/**` | kit | init/update, replaced on update |
| `.agents/kit/harness.sh` | kit | generated by init/update |
| `.agents/kit/hooks/pre-commit` | kit | mode `100755` recorded in the git index by init/update |
| `.agents/skills/**` (opencode's skills folder) | kit | init/update, replaced on update |
| `.agents/kit.lock` | kit | init/update |
| `AGENTS.md`, between the markers | kit | init/update |
| `AGENTS.md`, outside the markers | project | created from the template if missing |
| `GLOSSARY.md` | project | created from the template if missing |
| `docs/agents/project.md` | project | created from the template if missing |
| `docs/adr/` | project | `.gitkeep` created if the folder is missing |
| `.scratch/` | project | `.gitkeep` created if the folder is missing |
| `.agents/hooks.local/pre-commit` | project | never written by the kit |
| `.gitattributes` | project | one line appended if absent |
| `git config core.hooksPath` | — | set to `.agents/kit/hooks` |

**Kept** means the file already existed, so `init` left it byte for byte and says so in
its summary. This applies to `AGENTS.md`, `GLOSSARY.md`, and
`docs/agents/project.md`; only the kit block inside `AGENTS.md` is written. Nothing is
ever deleted outside the two kit-owned folders. `init` never commits. Its one index
change is the hook's executable bit: after writing the hook it runs

```
git update-index --add --chmod=+x .agents/kit/hooks/pre-commit
```

so a POSIX checkout gets a hook git will actually run, even when the install happened
on Windows, where `core.filemode` is false and git would otherwise record `100644`.
Nothing else is staged, and this narrow exception to "the tool never stages or
commits" is the only one.

The summary lists what was created and kept, and which action was taken on the kit
block. Review and commit the result:

```
git status
git diff
git add .
git commit -m "Install the agent kit"
```

The pre-commit hook is active from the next commit. It refuses a `dev` commit made in
an agent session, refuses a commit when `.scratch` is gitignored, and validates the
issue tracker's invariants. It runs those checks with the project's `.venv`
interpreter when there is one; otherwise it uses `python3` only when that command
actually runs, which is what skips the Microsoft Store alias on Windows, and falls
back to `python`.

## Update a project

Run this from the project's git root, or pass the path:

```
agent-kit update [PATH]
```

`update` reads `.agents/kit.lock`, replaces `.agents/kit/` and the harness's skills
folder with the installed tool's payload, rewrites the kit block, resets
`core.hooksPath`, records the hook's executable bit in the index (the same
`git update-index --add --chmod=+x` step as `init`), and writes the new lock. It prints
`Updated agent-kit from X to Y.` and lists the files that were updated, added, or
removed.

It refuses when a kit-owned file was changed in the project — edited, deleted, or
added under one of the kit-owned folders — or when the kit block in `AGENTS.md` was
edited. The message names every affected path and the reason. Nothing is written when
any check fails. Kit-owned files are changed in the agent-kit repository, not in a
project: make the change there, release a new version, and run `agent-kit update`.

Templates are not re-created by `update`, so a project that deleted `GLOSSARY.md` keeps
it deleted. `.agents/hooks.local/` is never touched.

Exit codes are `0` for success, `1` for a refusal, and `2` for a usage error such as a
missing lock or a folder that is not a git root.

## `--force`

`--force` discards local changes instead of refusing. For `init` it deletes conflicting
files in the two kit-owned folders; for `update` it discards the changed, deleted, or
extra kit-owned files.

It never deletes silently. It lists the paths it will really delete and asks for a
typed confirmation:

```
These paths will be deleted:
...
Type 'yes' to delete them and continue:
```

`update` never deletes `AGENTS.md`; it only rewrites the kit block. A changed or
missing block is therefore reported on a line of its own, after the paths, if any:

```
These paths will be deleted:
...
The kit block in AGENTS.md will be replaced.
Type 'yes' to delete them and continue:
```

When only the block changed, there is no deletion heading and no empty list:

```
The kit block in AGENTS.md will be replaced.
Type 'yes' to continue:
```

Only the exact answer `yes` continues. Anything else prints `Aborted. Nothing was
changed.` and exits `1`. Without an interactive terminal the command is refused
outright, so an agent session cannot use `--force`.

Every check runs before the confirmation, so a run that would be refused — a broken kit
block in `AGENTS.md`, for example — is refused without asking and with nothing deleted.

## Project-specific steps

The kit's hook runs these project-owned files if they exist, and never creates them.

- **`.agents/hooks.local/pre-commit`** — optional extra pre-commit steps. The kit's
  hook runs it after the tracker check, from the project root, with `PYTHON` (the
  interpreter it resolved), `branch` (the branch being committed) and
  `PROTECTED_BRANCH` (the branch the kit protects, `dev`) exported. A non-zero exit
  refuses the commit with that status. This is where a project's own tests, linters,
  or release build go.

  The kit never writes this file, so it cannot record the mode for you: git must see
  it as executable, or a POSIX checkout silently skips it. After staging it, run

  ```
  git add --chmod=+x .agents/hooks.local/pre-commit
  ```

  and check the result with `git ls-files -s .agents/hooks.local/pre-commit`, which
  must report `100755`. On a Windows checkout with `core.filemode` off, use
  `git update-index --add --chmod=+x .agents/hooks.local/pre-commit` instead.
- **`docs/agents/project.md`** — the project's rules for agents: the command that runs
  the test suite, generated or protected paths, release steps, ADR numbering, and
  anything else an agent must know before editing.
- **`GLOSSARY.md`** and **`docs/adr/`** — the project's vocabulary and architecture
  decisions, following the conventions the kit installs under `.agents/kit/`.

## Maintaining the kit

Kit content lives in `src/agent_kit/payload/`:

- `kit/` becomes `.agents/kit/` in a project;
- `skills/` becomes the harness's skills folder;
- `templates/` holds the project-owned starters;
- `agents-block.md` is the block written into `AGENTS.md`.

Two rules keep packaging predictable: no file in `payload/` may start with a dot, and
no file directly in `payload/skills/` may end in `.md` (opencode would load it as a
skill). Files the tool needs that start with a dot are written by code instead.

After editing the payload, run the whole suite from the repository root:

```
py -3.14 -m unittest discover -s tests -t . -v
```

`tests/test_packaging.py` builds a wheel and checks that it carries every payload file.
It may need network access for the build's isolated environment and can be skipped with
the `SKIP_PACKAGING_TEST` environment variable set.

### Bumping the version

The version lives in two files, and both change together; a test fails when they
disagree.

1. Set the new version in `src/agent_kit/__init__.py` and `pyproject.toml`.
2. Add a `CHANGELOG.md` entry under a new `## [X.Y.Z] - YYYY-MM-DD` heading and update
   `VERSION_HEADING` in `tests/test_changelog.py` to match. `CHANGELOG.md` states the
   SemVer policy.
3. Run the suite.
4. Refresh this repo's installed copy from the repository root with `PYTHONPATH=src`,
   so `.agents/kit.lock` records the new `kit_version`:

   ```
   py -3.14 -m agent_kit update
   ```

   On PowerShell, set `$env:PYTHONPATH = "src"` first.
5. Run `py -3.14 tools/check_payload_sync.py`.
6. Commit. The user merges `agent/<feature-slug>` into `dev` and tags `vX.Y.Z` there;
   the tool reads its version from `src/agent_kit/__init__.py`.
7. Verify `agent-kit --version` reports the new version.

A bump is harness-neutral: `src/agent_kit/harness.py` only selects the skills folder
and the agent markers, and `installer` records the harness name in the lock's
`harness` field. Nothing about the version changes with the harness.

To refresh the vendored skill library, from the repository root:

```
python tools/refresh_skills.py <full-40-character-sha>
```

The tool downloads that commit from `https://github.com/mattpocock/skills`, validates
it, and replaces `src/agent_kit/payload/skills/` in one swap: the four categories, the
upstream `LICENSE`, and an `UPSTREAM` record with the commit and fetch date. It leaves
out `skills/deprecated/` and `skills/engineering/setup-matt-pocock-skills/`, and writes
nothing if validation fails. Run the tests afterwards.
